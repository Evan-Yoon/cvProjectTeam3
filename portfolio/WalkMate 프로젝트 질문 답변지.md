## A. 프로젝트 전체 이해도

### A1. WalkMate는 어떤 문제를 해결하려고 만든 서비스인가요?

**답변**

시각장애인 길을 걸어가기 위해서 하얀지팡이를 사용하여 앞에 물체가 있는지를 탐지합니다. 이때 하얀지팡이를 사용해서 탐지할 수 있는 거리는 1m정도입니다. 저희는 1m 밖에 있는 물체를 탐지해서 시각장애인의 안전한 보행을 보조해주는 서비스입니다.

**채점: 3 / 5**

**피드백**

문제의식은 좋습니다. “흰지팡이로 탐지하기 어려운 거리의 위험 객체를 미리 감지한다”는 설명은 서비스 필요성을 잘 보여줍니다. 다만 답안지 기준 핵심은 단순 객체탐지가 아니라 **음성 목적지 입력 → 경로 안내 → 카메라 객체탐지 → 신고 저장 → 관리자 확인**까지 이어지는 서비스 흐름입니다. 면접에서는 “위험 객체를 감지해서 알려주는 앱”에서 끝내지 말고, 신고와 운영자 확인까지 연결한 풀스택 서비스라고 말하는 편이 더 좋습니다.

### A2. 사용자가 위험 객체를 감지한 뒤 관리자 화면에 보이기까지 흐름을 설명해보세요.

**답변**

사용자 휴대폰(ios)디바이스에서 3초에 한번 사진을 찍으면 tflite 모델에 input이 되어 객체 탐지 정보가 출력됩니다. 만약에 객체가 탐지되었으면 fastapi 서버로 http post 요청을 보냅니다. 그러면 fastpi서버에서는 다시 aws s3로 사진 객체를 보내고, postgresql을 활용하는 supabase에 사진이 찍힌 위치정보나, 객체에 대한 정보를 보냅니다. 그러면 관리자 페이지에서 s3와 supabase에서 fastapi서버에서 정보를 받아와서 객체 탐지 정보와 위치정보를 보여줍니다.

**채점: 4 / 5**

**피드백**

큰 흐름은 거의 맞습니다. iOS WebView에서 TFLite 추론을 하고, 객체가 감지되면 FastAPI로 `POST` 요청을 보내며, 백엔드가 S3와 Supabase PostgreSQL에 나눠 저장한다는 설명은 좋습니다. 다만 관리자 UI는 현재 구조상 **Supabase `reports` 테이블을 직접 조회하고 Realtime INSERT를 구독**합니다. “S3와 Supabase에서 FastAPI 서버에서 정보를 받아온다”는 표현은 다소 부정확합니다. “이미지 URL은 DB에 저장되고, 관리자 UI는 DB row의 `image_url`을 사용해 S3 이미지를 보여준다”라고 정리하면 더 정확합니다.

**채점: 4 / 5**

역할을 솔직하게 구분한 점이 좋습니다. “당시에는 AI 모델 중심, 이후 포트폴리오 정리 과정에서 iOS React+Capacitor userUI와 전체 흐름 연결을 직접 검증했다”는 식으로 말하면 신뢰도가 높습니다. 다만 면접 답변으로는 문장이 길고 방어 지점이 많습니다. “팀 프로젝트 당시 담당 범위”와 “이후 개인적으로 보완한 범위”를 분리해서 말하면 더 깔끔합니다.

## B. AI 모델 / 객체탐지

### B1. 왜 점자블록 파손 탐지에서 보행 위험 객체 탐지로 방향을 바꿨나요?

**답변**

처음 프로젝트 기획에서는 시각장애인이 점자블록을 따라갈 수 있게 점자블록을 탐지하는 서비스를 기획했었습니다. 추가적으로 파손된 점자블록을 자동으로 정부부처에 신고할 수 있도록 하는 서비스를 생각했습니다. 하지만 프로젝트가 진행됨에 따라, 현실의 시각장애인을 생각해 보았을때, 이미 점자블록은 잘 탐지하시고 계실 것이라고 생각되었고, 심지어 점자블록이 어느정도 이상 손상되었을때는 오히려 점자블록으로 인식하기 어려운 수준이 되어버려서 객체탐지가 불가능했습니다. 추가적으로 실제로 길가로 나가서 현장조사를 해본 결과, 많이 개발된 지역 외에는 오히려 점자블록이 없는 상황이 많았습니다. 이로인해 점자블록 탐지 모델 개발에서 일반적으로 길거리에서 마주칠 수 있는 객체들을 탐지하고 거리를 측정해서 사전에 알림을 줄 수 있는 서비스로 기획방향성을 수정했습니다.

**채점: 4.5 / 5**

**피드백**

답안지의 핵심과 잘 맞습니다. 파손이 심하면 오히려 점자블록의 형태가 사라져 탐지가 어렵다는 점, 실제 현장에서는 점자블록이 없는 구간도 많다는 점을 잘 설명했습니다. 마지막 문장의 “거리 측정”은 현재 코드에서 bbox 크기 기반 추정에 가깝고 정밀 거리 센서가 아니므로, 면접에서는 “거리를 정밀 측정한다”보다 “위험 객체를 감지하고 대략적인 방향/거리 힌트를 제공한다” 정도로 낮춰 말하는 편이 안전합니다.

### B2. COCO와 Roboflow 데이터를 통합한 이유는 무엇인가요?

**답변**

시각장애인이 인도를 걸어다니면서 만날수 있는 것들 중 대중적인 것들만 우선적으로 탐지하는 것을 저희 프로젝트의 mvp로 잡았습니다. COCO 데이터셋은 쉽게 받아볼 수 있었기 때문에 기존에 COCO 데이터셋에서 탐지되는 라벨들 중 인도 위에서 자주 접하는 강아지, 사람, 벤치 등과 더불어 차도에 다니는 위험한 객체들, 예를 들어 차, 버스, 트럭, 등 또한 횡단보도를 건널때 위험한 것들의 예시인 스탑 사인과 신호등 등을 활용하기 위해 COCO 데이터셋을 사용했습니다. 그외에도 저희가 현장조사를 나갔을때 인도위에서 시각장애인이 불편할만한 것들을 찾아보니, 넘어져있는 킥보드 또는 이상하게 세워져 있는 킥보드가 가장 컸고, bollard라는 것도 의외로 위험하게 중간중간에 세워져 있었습니다. 그래서 Roboflow 데이터도 같이 활용하게 되었습니다.

**채점: 4 / 5**

**피드백**

COCO와 Roboflow의 역할 구분은 잘 설명했습니다. COCO는 일반 객체, Roboflow는 킥보드와 볼라드 같은 프로젝트 특화 객체를 보강했다는 흐름이 명확합니다. 답안지 기준으로는 여기에 한 문장만 더 붙이면 좋습니다. “각 데이터를 따로 순차 학습하면 기존 클래스 성능이 떨어지는 catastrophic forgetting 위험이 있어, 전체 클래스를 한 번에 통합 학습했다”라고 말하면 모델 학습 전략까지 설명됩니다.

### B3. baseline, adamw_cos, heavy_aug 중 baseline을 선택한 이유는 무엇인가요?

**답변**

3가지 모델을 다양하게 하이퍼파라미터 조정을 통해 비교를 했을때 baseline 모델이 가장 탐지성능이 좋았기 때문입니다.

**채점: 2.5 / 5**

**피드백**

방향은 맞지만 너무 짧습니다. 답안지에는 baseline의 지표가 구체적으로 있습니다. 면접에서는 최소한 “Precision 0.7551, Recall 0.6053, mAP50 0.6772, mAP50-95 0.4768로 세 실험 중 가장 높았다” 정도는 말해야 합니다. 숫자를 모두 외우기 어렵다면 “mAP50과 mAP50-95가 baseline에서 가장 좋았다”라고라도 답하는 것이 좋습니다.

### B4. YOLO 모델을 앱에서 쓰기 위해 어떤 변환 과정을 거쳤나요?

**답변**

기존 pt 형식의 모델을 가볍게 변환한 tflite모델로 변환하기 위해서 먼저 onnx 모델로 바꾼 다음에 tflite로 변환했습니다. 사실 이때 int8 모델을 활용하려고 했는데, capacitor에서 웹뷰에서의 기능을 가져다가 활용해야 하는데, int8로 양자화한 모델을 활용했을때 오히려 성능이 더 느려지는 결과를 확인하고, 기본 best_float32.tflite를 활용하게 되었습니다. 사실 정확히 어떠한 이유로 float32보다 int8 모델이 더 느리게 작동하게 되는지는 잘 알지는 못합니다.

**채점: 3.5 / 5**

**피드백**

`pt → ONNX → TFLite` 흐름은 맞고, INT8보다 float32가 WebView/tfjs-tflite 환경에서 더 나았다는 경험도 좋은 답변 포인트입니다. 다만 답안지 기준 변환 흐름은 `best.pt → ONNX → SavedModel → TFLite float32`입니다. 최종 파일이 `best_float32.tflite`이고, 앱의 `public/wasm`과 iOS bundle에 같은 파일이 들어간다는 점까지 말하면 더 강합니다. “왜 INT8이 느렸는지 정확히 모른다”는 답은 괜찮지만, “WebAssembly 런타임에서는 양자화 모델이 항상 빠르지 않을 수 있어 실측 결과 기준으로 float32를 선택했다”라고 정리하면 방어가 됩니다.

### B5. TFLite 출력 `[1,16,8400]`을 어떻게 해석했나요?

**답변**

잘은 모르지만 제가 아는대로 설명해보자면, 앞에 1은 배치 사이즈 같고 뒤에 16은 yolo에서 4*4로 사진을 나눈 것에 대한 내용 같고, 8400은 pixel별 정보와 라벨에 대한 정보로 예상됩니다. 사실 제가 아는 이 내용은 you only look once 논문에 대한 설명을 하는 유튜브를 보고 알게 된 내용으로 추측해보았습니다.

**채점: 1 / 5**

**피드백**

이 답변은 반드시 고쳐야 합니다. `1`은 batch size로 볼 수 있어 맞지만, `16`은 4x4 grid가 아니라 **bbox 4개 값 + 클래스 score 12개**입니다. `8400`은 pixel별 정보가 아니라 여러 feature map 위치에서 나온 후보 박스 수로 보는 것이 맞습니다. 현재 프로젝트의 `YoloParser`도 이 구조를 기준으로 confidence threshold와 NMS를 적용합니다. 면접에서는 “정확히 모르겠습니다”보다 “16은 bbox 4 + class 12, 8400은 후보 박스 수”라고 짧게라도 말해야 합니다.

## C. 백엔드 / API 설계

### C1. 왜 앱이 Supabase나 S3에 직접 접근하지 않고 FastAPI를 거치게 했나요?

**답변**

사실은 네트워크와 보안에 대해서 잘 알지는 못하지만, supabase나 s3 로 접근하기 위해서는 key가 필요한데, 이때 이 키는 디바이스 수준에서 관리하면 노출이 되기 때문에 중간 서버에서 관리하는 것으로 알고 있습니다.

**채점: 4 / 5**

**피드백**

핵심은 맞습니다. DB 비밀번호, AWS key, TMAP key 같은 민감한 값을 앱에 직접 넣으면 노출 위험이 있으므로 FastAPI를 보안 경계로 둔다는 설명이 좋습니다. 다만 “잘 알지는 못하지만”으로 시작하면 답변 신뢰도가 낮아집니다. “클라이언트에는 신고 요청만 맡기고, S3 업로드와 DB 저장은 서버에서 처리하게 해 키 노출을 막았습니다”라고 단정적으로 말하는 편이 좋습니다.

---

### C2. 주요 API 엔드포인트를 설명해보세요.

**답변**

엔드포인트는 api 통신을 하기 위해 노출되는 부분으로 알고 있습니다. 먼저 백엔드 서버가 있고 백엔드 서버에서는 supabase로 값을 보내거나 받는 post/get엔드포인트가 각각 있을 것이고, S3로도 보내거나 받는 엔드포인트다 각각 있을 것이고, 관리자 페이지로 데이터를 보내고 받는 엔드포인트가 각각 있을 것이고, 하나더 기억하는게 관리자 페이지에서는 삭제 요청, 정확히 말하자면 deleted_at이라는 열에 현재시간을 추가하는 post 엔드포인트가 있을 것이고, 사용자 user로 데이터를 받는 엔드포인트가 있을 것입니다. 그리고 지금까지 말한 서버의 엔드포인트에 반대편 즉, supabase, s3, 관리자페이지, 유저앱에 각각 맞는 엔드포인트도 있을것입니다.

**채점: 1 / 5**

**피드백**

현재 프로젝트 근거와 많이 다릅니다. 답안지 기준 주요 API는 정확히 6개입니다. `GET /health`, `POST /api/v1/reports/`, `POST /api/v1/navigation/path`, `GET /api/v1/reports/`, `PATCH /api/v1/reports/{id}`, `DELETE /api/v1/reports/{id}`입니다. ### E4. iPhone 실기기 테스트에서 어떤 문제가 있었고 어떻게 확인했나요?

운영 데이터 관리 기능이라는 방향은 맞습니다. 다만 현재 구현 기준으로는 일반 텍스트 검색보다 상태/위험도/날짜 필터, 정렬, 페이지네이션, CSV 내보내기가 핵심입니다. “반복 위험 지점이나 처리 대상을 빠르게 찾고, CSV로 외부 보고서나 지자체 전달 자료에 활용하기 위해 필요하다”라고 보강하면 좋습니다.

### F4. 관리자 UI가 Supabase를 직접 조회하고 상태 변경은 FastAPI를 쓰는 구조의 장단점은 무엇인가요?

**답변**

supabase를 직접 조회하게 되면 조금이라도 데이터의 이동시간을 줄이게 되면서 최종적으로 관리자가 좀더 데이터 변동을 빠르게 확인할 수 있습니다. 하지만 FastAPI로 상태를 변경하게 되는 것은 잘 모르겠읍니다.

**채점: 2.5 / 5**

**피드백**

Supabase 직접 조회의 장점은 잘 짚었습니다. Realtime 연결과 빠른 구현도 장점입니다. 하지만 단점이 중요합니다. 데이터 접근 책임이 프론트와 백엔드로 나뉘면 보안 정책과 일관성 관리가 복잡해집니다. 현재는 백엔드 숨김 처리가 `Hidden`을 저장하고 adminUI 직접 조회는 `hidden`을 제외하는 대소문자 불일치도 있습니다. 운영 환경에서는 조회와 상태 변경을 모두 백엔드로 모으거나, RLS 정책을 엄격히 설계해야 합니다.

## G. 인프라 / 배포 / 운영 관점

### G1. 어떤 값들을 환경 변수로 분리했고, 왜 분리했나요?

**답변**

엔드포인트와 key값들을 분리했습니다. 엔드포인트를 환경변수로 분리한 이유는 노출시 데이터 유출 및 조작 위험이 있기 때문입니다. 또한 key값역시 비슷한 이유로서, 데이터 유출 및 조작 위험이 있기 때문입니다.

**채점: 2.5 / 5**

**피드백**

환경 변수로 분리해야 한다는 방향은 맞습니다. 하지만 endpoint 자체는 보통 secret이라기보다 환경별 설정값에 가깝습니다. 정확한 값 이름을 말할 수 있어야 합니다. 백엔드는 `DATABASE_URL`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `S3_BUCKET_NAME`, `S3_PUBLIC_BASE_URL`, `TMAP_API_KEY`, `CORS_ORIGINS`를 사용합니다. userUI는 `VITE_BACKEND_URL`, `VITE_TMAP_API_KEY`, adminUI는 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_BACKEND_URL`을 사용합니다.

### G2. 실제 서비스로 운영한다면 프론트, 백엔드, DB, S3를 어떻게 배포하겠습니까?

**답변**

저희는 저희가 관리자인 상황까지만 생각을 해서 관리자 ui까지 배포할 생각은 없습니다. 하지만 실제로 유저 앱을 배포하게 된다면 백엔드와 관리자 ui 프론트는 vercel 등의 무료 배포 사이트에 각각 올려놓고, DB는 현재와 같이 supabase를 활용하고 S3도 그대로 활용하도록 할것입니다.

**채점: 2 / 5**

**피드백**

DB는 Supabase, 이미지는 S3를 유지한다는 부분은 맞습니다. 하지만 “관리자 UI를 배포할 생각이 없다”는 답은 실제 서비스 운영 질문에는 맞지 않습니다. 운영 서비스라면 관리자 UI도 인증 뒤 접근 가능하도록 배포해야 합니다. 답안지 기준으로는 프론트는 Vercel 또는 S3+CloudFront, 백엔드는 Docker 기반 ECS/EC2/Render 같은 서버 환경, DB는 Supabase PostgreSQL, 이미지는 S3, 백엔드는 HTTPS/CORS/auth/logging을 갖추는 방향이 좋습니다.

---

### G3. 운영 환경에서 어떤 로그와 지표를 봐야 하나요?

**답변**

잘 모르겟습니다.

**채점: 0.5 / 5**

**피드백**

운영 관점 핵심 질문입니다. 백엔드는 API 응답 시간, 4xx/5xx 에러율, S3 업로드 실패율, DB INSERT 실패율, TMAP API 실패율을 봐야 합니다. 앱에서는 GPS timeout, 모델 로드 실패, 추론 시간, 신고 전송 실패율을 봐야 합니다. 관리자 UI에서는 Realtime 연결 끊김, 데이터 조회 실패, 상태 변경 실패를 봐야 합니다.

### G4. TMAP API가 실패하거나 느릴 때 어떻게 대응하겠습니까?

**답변**

타임아웃 설정을 길게 해야 할것같고, 아예 안되면 저도 잘 모르겟습니다. 오류 메세지를 한번 음성으로 추가해서 한번만 알리고 계속 연동 확인하도록 해야 할 것 같습니다.

**채점: 2.5 / 5**

**피드백**

timeout과 사용자 안내를 언급한 점은 좋습니다. 다만 “길게”만 하는 것은 해결책이 아닙니다. timeout을 명시하고, retry를 제한적으로 적용하며, 사용자에게 안전한 메시지를 주고, 장애가 길어지면 마지막 성공 경로 캐싱, 대체 지도 API, 목적지 검색만 제공하는 fallback을 고려해야 합니다. 현재 `navigation.py`에는 timeout/retry가 명시되어 있지 않다는 점도 말할 수 있으면 좋습니다.

## H. 회고 / 개선 방향

### H1. 현재 프로젝트에서 가장 아쉬운 기술적 한계는 무엇인가요?

**답변**

객체탐지 모델의 라벨링의 다양성 부족과 객체 거리탐지기술의 임의성입니다. 실제로 길거리에서 볼 수 있는 다양한 객체들을 추가하여 학습시킴으로 라벨링의 다양성을 증대시키고, 실제 사용자의 키를 입력함으로써 하네스에 휴대폰을 장착해서 사용할 때의 핸드폰과 땅으로부터의 거리를 생각해서 사진에서 찍혔을 때의 x,y 좌표에 따라 거리를 유추하는 로직을 고도화하고 싶습니다.

**채점: 3.5 / 5**

**피드백**

AI 관점 한계는 구체적이고 좋습니다. 라벨 다양성, 거리 추정의 임의성, 실제 착용 조건을 고려한 보정은 좋은 회고입니다. 다만 답안지 기준 “가장 큰 기술적 한계”는 운영 보안과 런타임 안정성도 포함합니다. Supabase RLS/관리자 인증 부재, WebView 추론 성능, `Hidden`/`hidden` 상태 불일치, 실제 접근성 현장 테스트 부족까지 함께 말하면 풀스택 관점 답변이 됩니다.

### H2. 운영 수준으로 만들기 위해 가장 먼저 개선할 것은 무엇인가요?

**답변**

보안을 가장 먼저 개선해야 할 것 같습니다. 구체적으로 RLS 정책과 CORS 정책을 개선하고 싶습니다. 그 다음으로는 하드웨어적으로 서버 배포가 잘 유지될 수 있는 환경을 구축해야 할 것 같습니다.

**채점: 3.5 / 5**

**피드백**

보안을 1순위로 잡은 것은 답안지와 잘 맞습니다. 여기에 관리자 인증, API 인증, Supabase RLS, S3 접근 제어를 함께 말하면 더 정확합니다. “하드웨어적으로 서버 배포”보다는 “Docker 기반 백엔드 배포, HTTPS, 로그 수집, 장애 대응”처럼 소프트웨어 운영 관점으로 표현하는 편이 좋습니다. 또한 status enum 통일과 WebView 추론 성능 측정도 다음 우선순위로 넣으면 좋습니다.
