# 자기소개서

## 1. 지원 직무와 연결되는 핵심 역량

저는 React 기반 프론트엔드, FastAPI 백엔드, Supabase PostgreSQL, AWS S3, YOLO 기반 AI 모델을 하나의 서비스 흐름으로 연결한 경험이 있습니다. WalkMate 프로젝트에서 시각장애인을 위한 음성 기반 길안내와 보행 위험 요소 자동 신고 서비스를 구현하며, 사용자 앱, 관리자 웹, 백엔드 API, 데이터베이스, 이미지 저장소, 객체탐지 모델을 함께 다뤘습니다.

이 프로젝트에서 사용자는 iPhone 앱에서 음성으로 목적지를 입력하고, 앱은 GPS와 TMAP 경로 정보를 바탕으로 길안내를 제공합니다. 안내 중 카메라 프레임에서 위험 객체가 감지되면 이미지와 위치 정보가 FastAPI 백엔드로 전송되고, 백엔드는 이미지를 AWS S3에 업로드한 뒤 Supabase PostgreSQL의 `reports` 테이블에 신고 데이터를 저장합니다. 관리자는 React 기반 대시보드에서 신고 목록, 위험 히트맵, 상세 이미지, 처리 상태를 확인할 수 있습니다.

저는 이 과정을 통해 단일 기능만 구현하는 것이 아니라, 프론트엔드에서 발생한 사용자 이벤트가 백엔드, DB, 스토리지, 관리자 화면, AI 모델 추론까지 이어지는 전체 흐름을 설계하고 점검하는 경험을 쌓았습니다. 특히 풀스택 AI 개발자는 모델 성능만 보는 역할이 아니라, 모델 결과가 실제 사용자 경험과 운영 데이터로 안정적으로 이어지게 만드는 역할이라고 생각합니다.

## 2. React 기반 웹·앱 개발 경험

WalkMate의 사용자 앱은 React, Vite, TypeScript, Capacitor 기반의 iOS WebView 앱으로 구현했습니다. 공고에서 요구하는 React Native와 완전히 같은 구조는 아니지만, 웹 기술을 모바일 앱 환경에 연결하고 네이티브 권한, 위치 정보, 카메라, 음성 입출력, 실기기 테스트를 다뤘다는 점에서 크로스플랫폼 앱 개발에 가까운 경험을 했습니다.

사용자 앱에서는 화면을 단순 라우팅이 아니라 `IDLE -> LISTENING -> RETRY -> CONFIRMATION -> GUIDING` 상태 흐름으로 구성했습니다. 시각장애인 사용자를 고려해 작은 버튼 조작보다 음성 안내와 음성 입력이 자연스럽게 이어지도록 만들었고, 길안내 화면에서는 GPS, Leaflet 지도, TTS, STT, 카메라 객체탐지를 동시에 다뤘습니다.

실제 iPhone 12 mini에서 Xcode 로그를 보며 테스트한 것도 중요한 경험이었습니다. 브라우저에서 보이는 화면만 확인한 것이 아니라, iOS WebView 안에서 모델이 로드되는지, 카메라 프레임이 캡처되는지, Geolocation 요청이 지연되지 않는지, TTS/STT가 충돌하지 않는지, 백엔드 신고 요청이 실제로 전송되는지 확인했습니다. 이 과정에서 `localhost`가 iPhone에서는 Mac이 아니라 기기 자신을 의미한다는 점, 실기기 테스트에서는 네트워크 주소와 권한 설정이 기능 구현만큼 중요하다는 점을 직접 겪었습니다.

관리자 웹은 React, Vite, TypeScript 기반의 대시보드로 구현했습니다. Supabase `reports` 테이블을 조회해 신고 데이터를 가져오고, Realtime INSERT 구독으로 신규 신고를 화면에 반영했습니다. 대시보드에서는 전체 신고 수와 위험도 분포를 확인하고, 히트맵에서는 Leaflet 지도로 위험 위치를 확인하며, 마스터 DB 화면에서는 신고 목록 검색, 정렬, CSV 내보내기, 상세 모달, 상태 변경 기능을 제공했습니다. 사용자 앱이 현장에서 위험을 감지하는 화면이라면, 관리자 앱은 그 결과를 운영자가 실제로 관리할 수 있게 만드는 화면이었습니다.

## 3. 백엔드와 데이터베이스 설계 경험

백엔드는 FastAPI로 구성했습니다. 사용자 앱이 Supabase나 AWS 키를 직접 들고 있지 않도록, 위험 신고는 반드시 FastAPI를 거쳐 저장되게 설계했습니다. 사용자 앱은 `multipart/form-data`로 이미지 파일과 위치, 위험 객체 종류, 위험도, 설명을 전송하고, 백엔드는 이미지를 AWS S3에 업로드한 뒤 생성된 URL을 DB에 저장합니다.

Supabase는 Storage가 아니라 PostgreSQL DB와 Realtime 용도로 사용했습니다. 핵심 테이블인 `public.reports`에는 신고 ID, 위험 객체 종류, 위험도, 이미지 URL, 설명, 상태, 위치 geometry가 저장됩니다. 위치 정보는 PostGIS `geometry(Point, 4326)` 형태로 저장해 지도 기반 확장 가능성을 열어 두었습니다.

FastAPI에서는 신고 생성 외에도 관리자 신고 목록 조회, 상태 변경, 숨김 처리, TMAP 보행자 경로 API 프록시를 구현했습니다. 사용자 앱은 목적지 확정 후 백엔드의 경로 요청 API를 호출하고, 백엔드는 TMAP API 응답에서 안내 step과 polyline 좌표를 추출해 프론트엔드가 사용할 수 있는 형태로 반환합니다.

이 구조를 만들며 프론트엔드와 백엔드의 책임 분리도 배웠습니다. 사용자 앱이 DB에 직접 접근하지 않는 구조는 보안상 유리하지만, 관리자 UI는 현재 Supabase 직접 조회와 FastAPI 상태 변경 API를 함께 사용하고 있어 장기적으로는 읽기와 쓰기 경로를 통일해야 합니다. 또한 현재 Supabase RLS가 비활성화되어 있기 때문에, 운영 환경에서는 인증과 권한 정책을 반드시 다시 설계해야 한다고 정리했습니다. 구현한 부분과 아직 보완해야 할 부분을 구분해 보는 태도도 이 프로젝트에서 중요하게 배웠습니다.

## 4. AI 모델 개발 및 앱 탑재 경험

AI 모델은 YOLO11n 기반 객체탐지 모델을 사용했습니다. 보행 환경에서 의미 있는 객체를 탐지하기 위해 COCO 데이터에서 사람, 자전거, 자동차, 오토바이, 버스, 트럭, 신호등, 정지 표지판, 벤치, 반려견 등 10개 클래스를 선별했고, Roboflow 기반 데이터로 볼라드와 전동 킥보드를 추가해 총 12개 클래스로 구성했습니다.

학습은 `baseline`, `adamw_cos`, `heavy_aug` 세 가지 실험으로 비교했습니다. 최종 결과는 baseline이 precision 0.7551, recall 0.6053, mAP50 0.6772, mAP50-95 0.4768로 가장 안정적이었기 때문에 최종 모델로 선택했습니다. 단순히 모델을 한 번 학습하고 끝낸 것이 아니라, optimizer, learning rate, cosine scheduler, mixup 여부가 결과에 어떤 차이를 만드는지 비교해 선택 근거를 남겼습니다.

앱 탑재를 위해 PyTorch 모델인 `best.pt`를 TensorFlow Lite float32 형식의 `best_float32.tflite`로 변환했습니다. 로컬 macOS 환경에서는 TensorFlow/TFLite 변환 호환성 문제가 있어 Google Colab을 사용했고, 최종 변환 파일을 userUI의 WebAssembly 런타임에서 로드했습니다. 현재 앱은 `@tensorflow/tfjs-tflite`로 TFLite 모델을 불러오고, 카메라 프레임을 640x640 RGB 텐서로 전처리한 뒤 추론합니다.

모델 후처리도 직접 확인했습니다. TFLite export 로그의 출력 shape은 `(1, 16, 8400)`이었고, 이를 `4 bbox + 12 class score` 구조로 해석해 `YoloParser`에서 bounding box, class, confidence를 계산했습니다. confidence threshold는 0.30, NMS IoU threshold는 0.50으로 설정해 실제 앱에서 감지 결과가 지나치게 누락되지 않도록 조정했습니다.

AI 모델 개발에서 가장 크게 느낀 점은 데이터 정의의 중요성이었습니다. 처음에는 시각장애인을 위한 점자블록과 파손된 점자블록을 탐지하려 했지만, 실제 거리에는 점자블록이 없는 길도 많고, 파손이 심하면 오히려 점자블록이라는 형태 자체가 사라져 탐지하기 어렵다는 문제가 있었습니다. 결국 탐지 대상을 일반적인 보행 위험 요소로 재정의했고, 이 과정에서 모델 성능은 알고리즘만이 아니라 문제 정의와 라벨링 기준에 크게 좌우된다는 점을 배웠습니다.

## 5. 문제 해결 경험

가장 기억에 남는 문제 해결 경험은 실기기에서 객체탐지가 기대대로 동작하지 않았던 상황입니다. 처음에는 모델 로드 로그가 찍히는데도 감지 결과가 나오지 않았습니다. 단순히 “모델이 이상하다”고 판단하지 않고, 카메라 스트림 준비, 프레임 캡처, 입력 tensor shape, TFLite predict 시작, output shape, 파싱 박스 수를 순서대로 로그로 확인했습니다. 그 결과 모델 파일, 입력 전처리, 출력 shape 해석, confidence threshold, 후처리 로직을 분리해서 봐야 한다는 점을 정리할 수 있었습니다.

INT8 모델이 float32보다 느리게 동작했던 문제도 있었습니다. 일반적으로 INT8은 더 빠를 것이라고 예상했지만, iPhone WebView의 JavaScript/WebAssembly 환경에서는 런타임 최적화 방식에 따라 항상 빠르지 않을 수 있었습니다. 그래서 실제 로그와 체감 성능을 기준으로 float32 TFLite 모델로 되돌리고, 앞으로는 동일한 iPhone 프레임에 대해 PyTorch 모델, TFLite 모델, 앱 후처리 결과를 비교해야 정확도 저하 원인을 분리할 수 있다고 판단했습니다.

GPS timeout 문제도 실기기에서 확인했습니다. 위치 요청이 제한 시간 안에 끝나지 않으면 안내나 신고 흐름이 끊길 수 있기 때문에, 위치 옵션의 timeout과 maximumAge를 조정하고, 위치 정보가 늦게 들어오는 상황을 고려해야 했습니다. 음성 기능에서도 TTS 직후 STT가 바로 시작되면 입력이 충돌할 수 있어, TTS와 STT 전환 타이밍, iOS partial result 처리, 재입력 화면 흐름을 함께 점검했습니다.

백엔드와 데이터 저장에서도 문제를 나눠 보았습니다. 신고 이미지는 Supabase Storage가 아니라 AWS S3에 저장되므로, 이미지가 보이지 않는 문제는 Supabase가 아니라 S3 URL, 버킷 공개 정책, `S3_PUBLIC_BASE_URL` 설정에서 발생할 수 있습니다. 또한 관리자 UI의 숨김 처리에서 status 값의 대소문자 불일치 가능성이 있어, 새로고침 후 숨김 데이터가 다시 보일 수 있다는 위험도 문서화했습니다. 저는 이런 문제를 숨기기보다 현재 상태와 개선 방향을 명확히 구분하는 것이 더 좋은 개발 태도라고 생각합니다.

## 6. AI 개발 도구 활용과 성장 태도

저는 개발 과정에서 Codex와 같은 AI 개발 보조 도구를 단순 코드 생성기가 아니라 코드베이스 검토와 문제 분해를 돕는 도구로 활용했습니다. 예를 들어 프로젝트 문서를 작성할 때 실제 파일 구조와 맞지 않는 설명이 있는지 검색하고, 모델 파일 경로와 앱 런타임 설정이 일치하는지 확인하며, Xcode 로그를 바탕으로 객체탐지 루프의 어느 단계에서 문제가 생기는지 정리했습니다.

AI 도구를 사용할 때도 중요한 것은 결과를 그대로 믿는 것이 아니라, 실제 코드와 로그로 검증하는 태도라고 생각합니다. WalkMate 문서를 정리하면서 Android 네이티브 플러그인, Docker, CI/CD, 운영 배포처럼 현재 저장소에서 증거가 부족한 항목은 구현 완료로 쓰지 않고 한계와 개선 방향으로 분리했습니다. 이 경험은 AI 도구를 활용하더라도 개발자는 사실 확인과 책임 있는 판단을 해야 한다는 점을 배우게 해 주었습니다.

새로운 기술을 접할 때도 먼저 작은 흐름을 동작시키고, 그 다음 실제 서비스 구조로 연결하는 방식을 선호합니다. WalkMate에서는 React 앱에서 시작해 Capacitor iOS WebView, FastAPI, Supabase, S3, YOLO/TFLite까지 범위를 넓혔습니다. 익숙하지 않은 기술이 있어도 문서와 로그, 실제 동작 결과를 바탕으로 빠르게 학습하고 적용하는 편입니다.

## 7. 입사 후 기여 방향

(주)케이엘피의 React / React Native 웹·앱 풀스택 AI 개발자 직무에서는 프론트엔드, 앱, 백엔드, 데이터베이스, AI 도구 활용 능력을 함께 요구한다고 이해했습니다. 저는 WalkMate 프로젝트를 통해 이 요소들이 서로 분리된 기술 목록이 아니라 하나의 사용자 문제를 해결하기 위해 연결되어야 한다는 점을 경험했습니다.

입사 후에는 React 기반 UI 구현뿐 아니라, 모바일 환경에서의 권한 처리, 위치 정보, 네이티브 기능 연동, API 통신 문제를 빠르게 파악해 기여하고 싶습니다. React Native 자체는 앞으로 더 깊게 익혀야 할 영역이지만, Capacitor 기반 iOS WebView에서 실기기 테스트와 네이티브 권한 이슈를 다룬 경험을 바탕으로 React Native 앱 개발 환경에도 빠르게 적응할 수 있습니다.

백엔드 측면에서는 FastAPI로 구현했던 신고 저장, 관리자 API, TMAP 프록시 경험을 바탕으로 Node.js, NestJS, Express 기반 API 구조도 적극적으로 학습하고 적용하겠습니다. RDB 설계에서는 Supabase PostgreSQL과 PostGIS를 사용하며 위치 데이터, 신고 상태, 이미지 URL, Realtime 구독 흐름을 다뤘고, 이를 더 발전시켜 운영 환경에서 필요한 인증, 권한, migration, 로깅, 모니터링까지 체계적으로 다루고 싶습니다.

인프라와 배포 측면에서는 AWS S3를 실제 이미지 저장 흐름에 연결했지만, Docker와 CI/CD는 아직 운영 수준으로 구축했다고 말하기 어렵습니다. 그래서 이 부분은 입사 후 가장 먼저 보완하고 싶은 영역입니다. 프로젝트를 컨테이너화하고, 테스트와 빌드를 자동화하며, 프론트엔드와 백엔드가 안정적으로 배포되는 과정을 직접 책임질 수 있는 개발자가 되고 싶습니다.

저는 새로운 도구를 빠르게 받아들이되, 그 결과를 실제 코드와 사용자 흐름으로 검증하는 개발자가 되고자 합니다. WalkMate에서 배운 가장 큰 교훈은 좋은 서비스는 프론트엔드, 백엔드, 데이터, AI 모델 중 하나만 잘해서 만들어지지 않는다는 점입니다. 사용자가 겪는 문제를 중심에 두고, 필요한 기술을 끝까지 연결해 동작하게 만드는 풀스택 AI 개발자로 성장하겠습니다.
