## A1. WalkMate는 어떤 문제를 해결하려고 만든 서비스인가요?

**답변:**
WalkMate는 시각 정보 접근이 어려운 보행자가 목적지를 음성으로 입력하고, 경로 안내를 받으면서 주변 위험 객체를 자동으로 감지·신고할 수 있게 만든 서비스입니다. 단순 길안내 앱이 아니라, **음성 입력, 위치, 지도, 카메라 객체탐지, 신고 저장, 관리자 확인**까지 하나의 흐름으로 연결한 점이 핵심입니다. 현재 `README.md`와 포트폴리오 문서도 “감지 → 신고 → 저장 → 운영 확인” 흐름을 핵심으로 설명합니다.

## A2. 위험 객체 감지부터 관리자 화면까지 흐름을 설명해보세요.

**답변:**
사용자 iPhone 앱에서 `VisionCamera.tsx`가 카메라 프레임을 캡처하고, WebView 안에서 TFLite 모델로 위험 객체를 탐지합니다. 위험 객체가 감지되면 `src/api/report.ts`가 이미지, 위치, 위험도, 객체 라벨을 `multipart FormData`로 FastAPI 백엔드에 보냅니다. 백엔드는 이미지를 S3에 업로드하고, DB에는 이미지 URL과 신고 메타데이터, PostGIS 좌표를 저장합니다. 이후 관리자 UI는 Supabase `reports` 테이블을 직접 조회하고, Realtime INSERT 구독으로 새 신고를 새로고침 없이 반영합니다.

## B1. 왜 점자블록 파손 탐지에서 보행 위험 객체 탐지로 바꿨나요?

**답변:**
점자블록 파손은 문제가 심할수록 오히려 원래 형태가 사라져 모델이 학습하기 어렵다는 문제가 있었습니다. 그래서 “파손된 점자블록”이라는 좁은 객체보다, 실제 보행 중 위험이 되는 자동차, 자전거, 킥보드, 볼라드, 사람, 개 같은 객체로 문제를 재정의했습니다. 즉, 모델이 안정적으로 인식할 수 있고 사용자에게 즉시 의미 있는 위험 정보를 주는 방향으로 바꾼 것입니다.

## B2. COCO와 Roboflow 데이터를 통합한 이유는 무엇인가요?

**답변:**
COCO에는 사람, 자동차, 버스, 자전거처럼 일반적인 객체 클래스가 있고, Roboflow에는 프로젝트에 필요한 볼라드와 킥보드 같은 커스텀 위험 객체가 있었습니다. 따로 순차 학습하면 기존 클래스 성능이 떨어지는 catastrophic forgetting 문제가 생길 수 있어서, 전체 클래스를 한 번에 학습시키는 통합 학습 전략을 선택했습니다. 이 판단은 `portfolio/Portfolio_AIEngineer.md`와 `model/exp_comparison/`의 실험 산출물 기준으로 설명할 수 있습니다.

## B3. baseline 모델을 최종 선택한 이유는 무엇인가요?

**답변:**
세 가지 실험 중 baseline이 Precision 0.7551, Recall 0.6053, mAP50 0.6772, mAP50-95 0.4768로 가장 우수했습니다. adamw_cos와 heavy_aug는 일부 개선을 기대했지만 전체 핵심 지표에서 baseline보다 낮았습니다. 그래서 “복잡한 튜닝을 많이 한 모델”보다 `model/exp_comparison/*/results.csv` 기준 지표가 가장 좋은 baseline을 앱 탑재 모델로 선택했습니다.

## B4. YOLO 모델을 앱에서 쓰기 위해 어떤 변환을 했나요?

**답변:**
학습된 PyTorch 기반 YOLO 모델을 앱 WebView에서 실행하기 위해 `best.pt → ONNX → SavedModel → TFLite float32` 흐름으로 변환했습니다. 최종 앱에는 `best_float32.tflite`를 탑재했고, `@tensorflow/tfjs-tflite`와 WebAssembly 런타임으로 iOS WebView 안에서 추론하도록 구성했습니다. 현재 파일 기준으로 `model/exp_comparison/baseline/weights/best_float32.tflite`, `UI/userUI/public/wasm/best_float32.tflite`, `UI/userUI/ios/App/App/public/wasm/best_float32.tflite`의 SHA-256도 동일합니다.

## B5. TFLite 출력 `[1,16,8400]`은 어떻게 해석했나요?

**답변:**
이 출력은 YOLO 계열 모델의 예측 결과 텐서입니다. 여기서 16은 `bbox 4개 값 + 클래스 score 12개`로 해석했고, 8400은 여러 feature map 위치에서 나온 후보 박스 수로 봤습니다. 후처리에서는 confidence threshold 0.30으로 낮은 확률 후보를 제거하고, NMS, 즉 Non-Maximum Suppression으로 겹치는 박스 중 가장 신뢰도 높은 박스만 남겼습니다. 현재 `VisionCamera.tsx`는 `YoloParser.parse(flat, shape, 0.3, 0.5)`를 호출하므로 NMS IoU 기준은 0.50입니다.

## C1. 왜 FastAPI를 서버 경계로 두었나요?

**답변:**
모바일 앱이 DB 비밀번호, AWS 키, TMAP 서버 키 같은 민감한 값을 직접 들고 있으면 보안상 위험합니다. 그래서 FastAPI를 중간 서버로 두고, 앱은 신고 요청과 경로 요청만 보내도록 했습니다. 실제 S3 업로드, DB 저장, TMAP 경로 요청은 백엔드가 처리하게 해서 클라이언트와 인프라 사이의 보안 경계를 만들었습니다.

## C2. 주요 API 엔드포인트를 설명해보세요.

**답변:**
주요 API는 6개입니다. `GET /health`는 서버 상태 확인, `POST /api/v1/reports/`는 위험 신고 생성, `POST /api/v1/navigation/path`는 TMAP 보행자 경로 프록시, `GET /api/v1/reports/`는 관리자 신고 목록 조회, `PATCH /api/v1/reports/{id}`는 처리 상태 변경, `DELETE /api/v1/reports/{id}`는 물리 삭제가 아니라 `status = 'Hidden'`으로 바꾸는 숨김 처리입니다.

## C3. 이미지를 DB가 아니라 S3에 저장한 이유는 무엇인가요?

**답변:**
이미지는 바이너리 파일이라 DB에 직접 넣으면 DB 크기, 백업, 조회 성능, 비용 관리가 불리해질 수 있습니다. 그래서 이미지는 S3에 저장하고, DB에는 `image_url`만 저장했습니다. 이렇게 하면 DB는 검색과 메타데이터 관리에 집중하고, S3는 파일 저장과 배포 역할을 맡게 됩니다.

## C4. S3 업로드는 성공했는데 DB 저장이 실패하면 어떻게 처리해야 하나요?

**답변:**
현재 코드에는 S3 업로드 성공 후 DB INSERT 실패를 보상하는 로직이 없습니다. 운영 수준으로 만들려면 S3 업로드 성공 후 DB 저장이 실패했을 때 업로드된 S3 객체를 삭제하거나, 실패 큐에 기록해 정리 작업을 수행해야 합니다. 반대로 DB 저장 후 후속 처리가 실패하는 흐름을 추가한다면 현재 status enum에 없는 `failed` 같은 상태를 설계해야 합니다. 핵심은 S3와 DB가 하나의 트랜잭션으로 묶이지 않기 때문에, 실패 지점을 명시하고 정리 전략을 갖는 것입니다.

## C5. 현재 구조에서 가장 큰 보안 취약점은 무엇인가요?

가장 큰 취약점은 인증과 권한 정책이 부족하다는 점입니다. 현재 `UI/adminUI/Supabase/tables.sql`은 로컬 테스트 편의를 위해 RLS, 즉 Row Level Security를 비활성화하고 있고, 관리자 UI에도 별도 로그인 검증이 없습니다. 운영 환경에서는 관리자 로그인, API 인증, Supabase RLS 정책, S3 접근 권한, CORS 제한을 먼저 정리해야 합니다.

## D1. `reports` 테이블에는 어떤 정보가 저장되나요?

**답변:**
`reports` 테이블에는 신고 ID(`item_id`), 생성 시각, 기기 ID(`device_id`), 위험 객체 종류, 위험도, 이미지 URL, 설명, 객체 라벨, 처리 상태, 위치 geometry가 저장됩니다. 테이블에는 `distance`, `direction`, `latitude`, `longitude` 컬럼도 있지만, 현재 백엔드 INSERT 로직의 핵심 좌표 저장은 PostGIS `location` 컬럼입니다. 신고 이미지는 S3에 있고, DB에는 그 URL과 위치·위험도·상태 같은 운영 메타데이터가 들어갑니다.

## D2. PostGIS Point를 쓴 이유는 무엇인가요?

**답변:**
단순 위도·경도 숫자로도 지도 표시는 가능하지만, PostGIS Point로 저장하면 이후 공간 검색과 거리 기반 쿼리에 유리합니다. 예를 들어 특정 반경 안의 반복 신고 지점 찾기, 위험 밀집 구역 분석, 지도 히트맵 확장 같은 기능을 만들기 좋습니다. 현재 `backend/app/crud/report.py`는 `ST_SetSRID(ST_MakePoint(:longitude, :latitude), 4326)`로 저장하고, 관리자 목록 조회에서는 `ST_Y(location)`과 `ST_X(location)`으로 위도·경도를 복원합니다.

## D3. Supabase Realtime은 어떤 역할을 하나요?

**답변:**
Supabase Realtime은 DB에 새 신고가 INSERT될 때 관리자 대시보드가 이를 구독해서 새로고침 없이 화면에 반영하게 해줍니다. 현재 `UI/adminUI/App.tsx`는 `postgres_changes`의 INSERT 이벤트를 구독합니다. 즉, 운영자가 페이지를 계속 새로고침하지 않아도 신규 위험 신고를 대시보드와 테이블에서 바로 확인할 수 있게 하는 역할입니다.

---

## D4. 운영 환경에서 RLS는 어떻게 설계하겠습니까?

**답변:**
먼저 사용자와 관리자를 분리하겠습니다. 일반 사용자는 직접 `reports`를 조회하지 못하고 신고 생성만 가능하게 하며, 관리자는 인증된 계정만 신고 조회·상태 변경을 할 수 있게 합니다. Supabase에서는 RLS를 켜고, role 또는 JWT claim 기준으로 `select`, `insert`, `update` 정책을 분리합니다. 더 엄격하게는 모든 쓰기 작업을 FastAPI를 통해 처리하고, Supabase anon key가 클라이언트에서 과도한 권한을 갖지 않도록 제한하겠습니다.

## E3. Capacitor를 쓴 장점과 한계는 무엇인가요?

## F2. 새 신고가 들어오면 관리자 화면은 어떻게 갱신되나요?

**답변:**
백엔드가 신고를 DB에 저장하면 Supabase Realtime이 INSERT 이벤트를 발생시키고, 관리자 UI가 그 이벤트를 구독해 새 신고를 화면에 반영합니다. 이를 통해 운영자는 새로고침 없이 대시보드와 테이블에서 신규 신고를 확인할 수 있습니다. 다만 현재 구독은 INSERT 중심이므로 상태 변경이나 숨김 처리까지 모든 화면에 실시간 반영하려면 UPDATE/DELETE 구독 또는 재조회 정책이 추가로 필요합니다.

---

## F3. 필터, 정렬, CSV 내보내기는 왜 필요하다고 봤나요?

**답변:**
관리자 대시보드는 단순히 신고를 보는 화면이 아니라 운영 데이터를 다루는 화면입니다. 현재 구현된 위험도별 필터, 상태별 필터, 날짜 필터, 정렬, 페이지네이션이 있어야 반복 위험 지점이나 처리 대상을 찾기 쉽습니다. CSV 내보내기는 신고 데이터를 외부 보고서, 지자체 전달 자료, 추가 분석 자료로 활용하기 위해 필요합니다. 일반 텍스트 검색은 운영 편의상 추가하면 좋은 다음 개선 항목으로 설명하는 편이 정확합니다.

---

## F4. Supabase 직접 조회와 FastAPI 상태 변경 구조의 장단점은 무엇인가요?

**답변:**
장점은 조회는 Supabase 클라이언트를 통해 빠르게 구현하고, Realtime도 쉽게 연결할 수 있다는 점입니다. 단점은 데이터 접근 책임이 프론트와 백엔드로 나뉘어 보안 정책이 복잡해질 수 있다는 점입니다. 현재 코드에는 백엔드 숨김 처리가 `Hidden`을 저장하는 반면 adminUI 직접 조회는 소문자 `hidden`을 제외하는 대소문자 불일치도 있습니다. 운영 환경에서는 조회와 상태 변경 모두 백엔드를 통하게 하거나, Supabase RLS 정책을 엄격히 설계해서 권한 경계를 명확히 해야 합니다.

## G1. 어떤 값들을 환경 변수로 분리했나요?

**답변:**
백엔드에서는 `DATABASE_URL`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, `S3_BUCKET_NAME`, `S3_PUBLIC_BASE_URL`, `TMAP_API_KEY`, `CORS_ORIGINS`를 환경 변수로 분리했습니다. 사용자 앱에서는 `VITE_BACKEND_URL`과 `VITE_TMAP_API_KEY`, 관리자 UI에서는 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_BACKEND_URL`을 분리했습니다. 이유는 환경별 설정을 바꾸기 쉽게 하고, 민감 정보를 코드에 직접 넣지 않기 위해서입니다.

---

## G2. 실제 운영 배포라면 어떻게 구성하겠습니까?

**답변:**
프론트는 Vercel이나 S3+CloudFront로 정적 배포하고, 백엔드는 Docker 기반으로 ECS, EC2, 또는 Render 같은 서버 환경에 올릴 수 있습니다. DB는 Supabase PostgreSQL을 유지하되 RLS와 백업 정책을 켜고, 이미지는 S3에 저장합니다. 백엔드에는 HTTPS, CORS 제한, 인증 미들웨어, 로그 수집을 붙이고, 관리자 UI는 로그인 이후 접근하도록 구성하겠습니다.

---

## G3. 운영 환경에서 어떤 로그와 지표를 봐야 하나요?

**답변:**
백엔드는 API 응답 시간, 4xx/5xx 에러율, S3 업로드 실패율, DB INSERT 실패율, TMAP API 실패율을 봐야 합니다. 앱에서는 GPS timeout, 모델 로드 실패, 추론 시간, 신고 전송 실패율을 봐야 합니다. 관리자 UI에서는 Realtime 연결 끊김, 데이터 조회 실패, 상태 변경 실패를 모니터링해야 합니다.

---

## G4. TMAP API가 실패하면 어떻게 대응하겠습니까?

**답변:**
현재 `navigation.py`는 TMAP 실패 시 `{"status": "error", "message": "TMAP API Error"}`를 반환하지만, timeout과 retry 정책은 명시되어 있지 않습니다. 개선한다면 첫째, 백엔드에서 timeout과 retry를 명시합니다. 둘째, 실패 응답을 그대로 앱에 던지지 않고 사용자에게 “경로를 불러오지 못했습니다. 다시 시도해주세요” 같은 안전한 메시지를 보냅니다. 셋째, 장애가 길어지면 마지막 성공 경로 캐싱, 대체 지도 API, 또는 목적지 검색만 제공하는 fallback을 고려할 수 있습니다. 중요한 것은 외부 API 실패가 앱 전체 장애로 번지지 않게 하는 것입니다.

## H1. 현재 프로젝트의 가장 큰 기술적 한계는 무엇인가요?

**답변:**
가장 큰 한계는 운영 보안과 런타임 안정성입니다. Supabase RLS와 관리자 인증이 아직 없고, iPhone WebView에서 `tfjs-tflite` 추론을 돌리는 구조는 발열·지연·배터리 문제가 생길 수 있습니다. 또한 status 값의 `Hidden`/`hidden` 대소문자 불일치처럼 운영 데이터 일관성 이슈도 남아 있습니다. 실제 시각장애인 사용 환경에서는 VoiceOver, 야외 소음, 화면 잠금, GPS 약한 환경 테스트가 더 필요합니다.

---

## H2. 운영 수준으로 만들기 위해 가장 먼저 개선할 것은 무엇인가요?

**답변:**
우선순위는 인증과 권한입니다. 현재는 기능 흐름을 증명하는 단계였고, 운영에서는 관리자 인증, API 인증, Supabase RLS, S3 접근 제어가 먼저 필요합니다. 그다음에는 status enum을 통일하고, WebView 추론 성능을 측정해 Core ML 네이티브 추론이나 서버 추론과 비교하겠습니다. 마지막으로 실제 접근성 현장 테스트를 통해 UX를 검증하겠습니다.

---

## H3. 사용자 수가 늘어나면 어떤 병목이 생길까요?

**답변:**
첫째, 신고 이미지 업로드가 많아지면 S3 업로드와 백엔드 multipart 처리 부하가 늘어납니다. 둘째, 관리자 UI가 직접 Supabase를 많이 조회하면 DB 읽기 부하가 늘 수 있습니다. 셋째, Realtime 구독자가 많아지면 실시간 이벤트 처리 비용이 커질 수 있습니다. 해결하려면 이미지 업로드 큐, 페이지네이션 강화, 인덱스 설계, 캐싱, 백엔드 중심 조회 API, rate limit이 필요합니다.

---

## H4. 이 프로젝트가 풀스택 개발자 역량을 어떻게 보여준다고 생각하나요?

**답변:**
이 프로젝트는 단순히 화면 하나나 모델 하나를 만든 것이 아니라, 사용자 앱, AI 모델, 백엔드 API, DB, S3, 관리자 대시보드까지 하나의 서비스 흐름으로 연결했습니다. 풀스택 개발자에게 중요한 것은 특정 기술 하나보다 **사용자 입력이 서버와 데이터 저장소를 거쳐 운영 화면까지 도달하는 전체 흐름을 이해하고 책임지는 능력**이라고 생각합니다. WalkMate는 그 흐름을 실제로 구현한 사례입니다.
