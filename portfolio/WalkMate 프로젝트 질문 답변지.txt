A. 프로젝트 전체 이해도
1. WalkMate는 어떤 문제를 해결하려고 만든 서비스인가요?

- 시각장애인 길을 걸어가기 위해서 하얀지팡이를 사용하여 앞에 물체가 있는지를 탐지합니다. 이때 하얀지팡이를 사용해서 탐지할 수 있는 거리는 1m정도입니다. 저희는 1m 밖에 있는 물체를 탐지해서 시각장애인의 안전한 보행을 보조해주는 서비스입니다.

2. 사용자가 위험 객체를 감지한 뒤 관리자 화면에 보이기까지 흐름을 설명해보세요.

- 사용자 휴대폰(ios)디바이스에서 3초에 한번 사진을 찍으면 tflite 모델에 input이 되어 객체 탐지 정보가 출력됩니다. 만약에 객체가 탐지되었으면 fastapi 서버로 http post 요청을 보냅니다. 그러면 fastpi서버에서는 다시 aws s3로 사진 객체를 보내고, postgresql을 활용하는 supabase에 사진이 찍힌 위치정보나, 객체에 대한 정보를 보냅니다. 그러면 관리자 페이지에서 s3와 supabase에서 fastapi서버에서 정보를 받아와서 객체 탐지 정보와 위치정보를 보여줍니다.

3. “AI·백엔드·프론트엔드 전 영역”이라고 했는데, 본인이 직접 구현한 부분과 팀원이 한 부분을 구분해보세요.

- 사실 저는 프로젝트 기간에서는 AI 모델, 즉 객체탐지 모델 개발을 담당했었습니다. 하지만 객체탐지 모델이 디바이스 위에서도 잘 작동하는지를 확인하기 위해서는 프론트엔드에서 작동을 해보아야 했습니다. 그래서 그때 프론트엔드의 카메라 부분만 개발을 참여했습니다. 하지만 최근 해당 프로젝트에 대해 정리하며 포트폴리오를 만들기 위해 직접 제 아이폰에서 작동시켜보고자 하면서, 기존 android 용 프로젝트였던 내용을 ios로 전반적으로 수정하며 User 관련 프론트엔드, 즉 react+capacitor 부분을 구현해보았고, 또한 전반적인 프로젝트 수준의 리팩토링을 진행하기도 했습니다.


B. AI 모델 / 객체탐지
1. 왜 점자블록 파손 탐지에서 보행 위험 객체 탐지로 방향을 바꿨나요?

- 처음 프로젝트 기획에서는 시각장애인이 점자블록을 따라갈 수 있게 점자블록을 탐지하는 서비스를 기획했었습니다. 추가적으로 파손된 점자블록을 자동으로 정부부처에 신고할 수 있도록 하는 서비스를 생각했습니다. 하지만 프로젝트가 진행됨에 따라, 현실의 시각장애인을 생각해 보았을때, 이미 점자블록은 잘 탐지하시고 계실 것이라고 생각되었고, 심지어 점자블록이 어느정도 이상 손상되었을때는 오히려 점자블록으로 인식하기 어려운 수준이 되어버려서 객체탐지가 불가능했습니다. 추가적으로 실제로 길가로 나가서 현장조사를 해본 결과, 많이 개발된 지역 외에는 오히려 점자블록이 없는 상황이 많았습니다. 이로인해 점자블록 탐지 모델 개발에서 일반적으로 길거리에서 마주칠 수 있는 객체들을 탐지하고 거리를 측정해서 사전에 알림을 줄 수 있는 서비스로 기획방향성을 수정했습니다.

2. COCO와 Roboflow 데이터를 통합한 이유는 무엇인가요?

- 시각장애인이 인도를 걸어다니면서 만날수 있는 것들 중 대중적인 것들만 우선적으로 탐지하는 것을 저희 프로젝트의 mvp로 잡았습니다. COCO 데이터셋은 쉽게 받아볼 수 있었기 때문에 기존에 COCO 데이터셋에서 탐지되는 라벨들 중 인도 위에서 자주 접하는 강아지, 사람, 벤치 등과 더불어 차도에 다니는 위험한 객체들, 예를 들어 차, 버스, 트럭, 등 또한 횡단보도를 건널때 위험한 것들의 예시인 스탑 사인과 신호등 등을 활용하기 위해 COCO 데이터셋을 사용했습니다. 그외에도 저희가 현장조사를 나갔을때 인도위에서 시각장애인이 불편할만한 것들을 찾아보니, 넘어져있는 킥보드 또는 이상하게 세워져 있는 킥보드가 가장 컸고, bollard라는 것도 의외로 위험하게 중간중간에 세워져 있었습니다. 그래서 Roboflow 데이터도 같이 활용하게 되었습니다.

3. baseline, adamw_cos, heavy_aug 중 baseline을 선택한 이유는 무엇인가요?

- 3가지 모델을 다양하게 하이퍼파라미터 조정을 통해 비교를 했을때 baseline 모델이 가장 탐지성능이 좋았기 때문입니다. 

4. YOLO 모델을 앱에서 쓰기 위해 어떤 변환 과정을 거쳤나요?

- 기존 pt 형식의 모델을 가볍게 변환한 tflite모델로 변환하기 위해서 먼저 onnx 모델로 바꾼 다음에 tflite로 변환했습니다. 사실 이때 int8 모델을 활용하려고 했는데, capacitor에서 웹뷰에서의 기능을 가져다가 활용해야 하는데, int8로 양자화한 모델을 활용했을때 오히려 성능이 더 느려지는 결과를 확인하고, 기본 best_float32.tflite를 활용하게 되었습니다. 사실 정확히 어떠한 이유로 float32보다 int8 모델이 더 느리게 작동하게 되는지는 잘 알지는 못합니다.

5. TFLite 출력 [1,16,8400]을 어떻게 해석했나요?

- 잘은 모르지만 제가 아는대로 설명해보자면, 앞에 1은 배치 사이즈 같고 뒤에 16은 yolo에서 4*4로 사진을 나눈 것에 대한 내용 같고, 8400은 pixel별 정보와 라벨에 대한 정보로 예상됩니다. 사실 제가 아는 이 내용은 you only look once 논문에 대한 설명을 하는 유튜브를 보고 알게 된 내용으로 추측해보았습니다.

C. 백엔드 / API 설계
1. 왜 앱이 Supabase나 S3에 직접 접근하지 않고 FastAPI를 거치게 했나요?

- 사실은 네트워크와 보안에 대해서 잘 알지는 못하지만, supabase나 s3 로 접근하기 위해서는 key가 필요한데, 이때 이 키는 디바이스 수준에서 관리하면 노출이 되기 때문에 중간 서버에서 관리하는 것으로 알고 있습니다.

2. 주요 API 엔드포인트를 설명해보세요.

- 엔드포인트는 api 통신을 하기 위해 노출되는 부분으로 알고 있습니다. 먼저 백엔드 서버가 있고 백엔드 서버에서는 supabase로 값을 보내거나 받는 post/get엔드포인트가 각각 있을 것이고, S3로도 보내거나 받는 엔드포인트다 각각 있을 것이고, 관리자 페이지로 데이터를 보내고 받는 엔드포인트가 각각 있을 것이고, 하나더 기억하는게 관리자 페이지에서는 삭제 요청, 정확히 말하자면 deleted_at이라는 열에 현재시간을 추가하는 post 엔드포인트가 있을 것이고, 사용자 user로 데이터를 받는 엔드포인트가 있을 것입니다. 
그리고 지금까지 말한 서버의 엔드포인트에 반대편 즉, supabase, s3, 관리자페이지, 유저앱에 각각 맞는 엔드포인트도 있을것입니다.

3. 신고 이미지를 DB에 직접 저장하지 않고 S3에 저장한 이유는 무엇인가요?

- 개발당시 서버의 저장고가 좁았기 때문입니다.

4. S3 업로드는 성공했는데 DB 저장이 실패하면 어떻게 처리해야 하나요?

- S3에 삭제 요청을 보내는 방식이 있을것같고, 휴대폰에 로컬 db를 만들어둬서 나중에 보낼 수 있도록 하는 방식이 있을것같고, 사실 실패한 파트에 따라서 처리방식이 다를 것 같습니다.

5. 현재 구조에서 가장 큰 보안 취약점은 무엇인가요?

- 일단 기억나는 것중 하나는 supabase에서 rls 기준을 지키지 못했다 라는것을 알고 있습니다. 사실 RLS 정책이 정확히 무엇인지는 알지 못하고 있습니다. 또한 제 기억으로는 aws S3의 정책에서 CORS 정책 에서 모든 ip에서 통신한다는 내용이 있었던것같습니다. 사실 백엔드 서버가 하나 정해지게 된다면, CORS 정책에서 고정 ip로 바꿔야 할 것 같습니다.

E. 프론트엔드 / 사용자 앱
1. IDLE → LISTENING → CONFIRMATION → GUIDING 상태 머신으로 나눈 이유는 무엇인가요?

- 일단 많은 페이지를 만들지 않은 이유는 시각에 제한이 있는 사용자의 편의성을 위해서 였습니다. 상태 머신이 어떤 의미인지는 모르겠습니다.

2. 시각장애인 사용자를 고려해 UI/UX에서 어떤 결정을 했나요?

- 먼저 화면 터치가 전혀 없이도 활용할 수 있도록 진행했습니다. 항상 음성인식 기능이 켜져있을 수 있도록 했습니다. 만약에 버튼 기능을 활용한다면, 휴대폰의 위 절반을 예, 아래 절반을 아니오 처럼 화면이 보이지 않아도 터치 조작이 용이할 수 있도록 설계했습니다.

3. React 웹앱을 Capacitor로 감쌌을 때 장점과 한계는 무엇인가요?

- native 보다는 해당 환경에 맞는 ui 느낌을 줄수는 없었습니다.
- 하지만 javascript만으로도 native와 거의 유사한 서비스를 제공할 수 있었습니다. 큰 capacitor의 라이브러리 시장을 활용한다면 충분히 native 못지 않은 서비스를 javascript 만으로도 구현이 가능한 것이 장점입니다.

4. iPhone 실기기 테스트에서 어떤 문제가 있었고 어떻게 확인했나요?

- 먼저 저는 기존 프로젝트에서 android 기기만을 대상으로 개발을 진행했기에, android studio로 iphone 작업도 할 수 있다고 처음에 잘못 알고 있었다가 제 휴대폰이 iphone이어서 개발하려고 보니 mac 환경에서만 작업이 가능하고, 또한 xcode라는 것을 활용해서 작업이 가능하다는 것을 알게 되었습니다. 기존 프로젝트에서 android 작업을 할때 android 기기가 스냅드래곤이라는 버전을 갖고 있었는데, 이 버전은 npu를 활용할 수 있었습니다. 그래서 이전 작업자는 추론 속도 증가를 위해 cpu가 아닌 npu를 사용해서 추론하도록 capacitor 를 통해 웹뷰와 연결할 수 있도록 java코드를 직접 작성해서 직접 만든 라이브러리처럼 개발을 진행했던 거였습니다. 하지만 저는 그 사실을 모른채 이 라이브러리의 내용을 그대로 swift 로 바꿔서 진행했지만, npu어쩌구 저쩌구라는 객체를 실행할 수 없다라는 그런 비슷한 에러를 보게 되었습니다. 계속 오류를 수정하다가 마침내 실제로는 없는 capacitor의 오픈 소스에 없는 라이브러리라는것을 알게 되었고, 심지어 npu를 사용하도록 만들어진 코드를 ios에는 사용할 수 없다라는 것을 알게 되었습니다. 하지만 오히려 ios에 대한 capacitor의 오픈소스 라이브러리에는 tflite를 잘 활용할 수 있도록 누군가가 만들어두어서 swift 코드를 직접 작성하지 않고도 오히려 더 쉽게 객체 탐지 모델을 연동할 수 있었습니다.

5. WebView에서 TFLite 추론을 돌릴 때 어떤 문제가 생길 수 있나요?
잘 모르겠습니다. 제가 알기로는 native에서 돌리는 것보다 성능이 좋지 않을 수 있다는 것 정도로 알고 있습니다.

F. 관리자 대시보드
1. 관리자 대시보드는 어떤 화면들로 구성되어 있나요?

- 사용자의 리포트로 정보가 취합되어 화면을 구성합니다. 먼저 위치 정보들을 활용하여 지도위에서 표기하는 화면과, 객체탐지된 정보가 S3에서 가져온 사진들위에 그려진 정보로 실제 사용자의 카메라에서 객체탐지된 화면을 재구성하여 보여줍니다. 

2. 새 신고가 들어오면 화면은 어떻게 갱신되나요?

- supabase의 realtime 기능을 활용하여 실시간으로 갱신됩니다.

3. 검색, 필터, 정렬, CSV 내보내기는 왜 필요하다고 봤나요?

- 전반적으로 데이터를 관리하는 페이지의 기본 기능이라고 생각했으며, 그중에서도 필터는 객체의 위험도에 따라 우선적관리에 용이할 수 있도록 하는 기능입니다.

4. 관리자 UI가 Supabase를 직접 조회하고 상태 변경은 FastAPI를 쓰는 구조의 장단점은 무엇인가요?

- supabase를 직접 조회하게 되면 조금이라도 데이터의 이동시간을 줄이게 되면서 최종적으로 관리자가 좀더 데이터 변동을 빠르게 확인할 수 있습니다. 하지만 FastAPI로 상태를 변경하게 되는 것은 잘 모르겠읍니다.

G. 인프라 / 배포 / 운영 관점

1. 어떤 값들을 환경 변수로 분리했고, 왜 분리했나요?

- 엔드포인트와 key값들을 분리했습니다. 엔드포인트를 환경변수로 분리한 이유는 노출시 데이터 유출 및 조작 위험이 있기 때문입니다. 또한 key값역시 비슷한 이유로서, 데이터 유출 및 조작 위험이 있기 때문입니다.

2. 실제 서비스로 운영한다면 프론트, 백엔드, DB, S3를 어떻게 배포하겠습니까?

- 저희는 저희가 관리자인 상황까지만 생각을 해서 관리자 ui까지 배포할 생각은 없습니다. 하지만 실제로 유저 앱을 배포하게 된다면 백엔드와 관리자 ui 프론트는 vercel 등의 무료 배포 사이트에 각각 올려놓고, DB는 현재와 같이 supabase를 활용하고 S3도 그대로 활용하도록 할것입니다.

3. 운영 환경에서 어떤 로그와 지표를 봐야 하나요?

- 잘 모르겟습니다.

4. TMAP API가 실패하거나 느릴 때 어떻게 대응하겠습니까?

- 타임아웃 설정을 길게 해야 할것같고, 아예 안되면 저도 잘 모르겟습니다. 오류 메세지를 한번 음성으로 추가해서 한번만 알리고 계속 연동 확인하도록 해야 할 것 같습니다.

H. 회고 / 개선 방향

1. 현재 프로젝트에서 가장 아쉬운 기술적 한계는 무엇인가요?

- 객체탐지 모델의 라벨링의 다양성 부족과 객체 거리탐지기술의 임의성입니다. 실제로 길거리에서 볼 수 있는 다양한 객체들을 추가하여 학습시킴으로 라벨링의 다양성을 증대시키고, 실제 사용자의 키를 입력함으로써 하네스에 휴대폰을 장착해서 사용할 때의 핸드폰과 땅으로부터의 거리를 생각해서 사진에서 찍혔을 때의 x,y 좌표에 따라 거리를 유추하는 로직을 고도화하고 싶습니다.

2. 운영 수준으로 만들기 위해 가장 먼저 개선할 것은 무엇인가요?

- 보안을 가장 먼저 개선해야 할 것 같습니다. 구체적으로 RLS 정책과 CORS 정책을 개선하고 싶습니다. 그 다음으로는 하드웨어적으로 서버 배포가 잘 유지될 수 있는 환경을 구축해야 할 것 같습니다.

3. 사용자 수가 늘어나면 어떤 병목이 생길까요?

- 잘 모르겠습니다.

4. 이 프로젝트가 풀스택 개발자 역량을 어떻게 보여준다고 생각하나요?

- 잘 모르겠습니다.
